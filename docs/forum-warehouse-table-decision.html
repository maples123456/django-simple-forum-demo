论坛数仓表：什么时候值得建立

从一个具体的 DAU 业务问题出发，学习如何判断应该保留原始事实、建立用户日表、产品日表， 还是只使用一次性 SQL、CTE 或视图。

一、原始数据表和数据仓库表是什么关系

原始数据通常应该先以可追溯的事实粒度保存，但并不是所有原始数据都要继续建立一张新表。 数据仓库表的下一层应该由业务问题、使用频率、数据粒度和性能要求决定。
数据层一行代表什么当前论坛对应对象主要作用
原始事实层一行一个原始事件或业务事实analytics_analyticsevent、forum_post保留事实、支持回溯和重算
清洗层一行一个通过基础质量和身份规则的事实合格登录普通用户事件统一过滤和数据质量规则
中间层一行一个用户每天的行为analytics_useractivitydaily复用用户级分析逻辑
汇总层一行一个日期的产品指标analytics_productmetricsdaily快速服务固定看板
维度层一行一个用户、板块或帖子属性实体用户、板块、帖子维度给事实表提供分析属性
“原始表之后一定要建立一张汇总表”并不是固定规则。正确的顺序是：先确定事实粒度， 再判断是否需要清洗层、中间层、维度层或汇总层。

二、判断是否建立数仓表的核心问题

不要从“这张表看起来有用”开始，而要从业务问题开始：

判断问题需要回答的内容对建表决策的影响
谁会使用？看板、运营、产品、数据分析还是一次性排错？使用者越多，越值得统一建表
多久使用一次？每次请求、每天、每周还是只用一次？频繁使用更适合预聚合
计算是否昂贵？是否需要大表扫描、复杂 JOIN、去重和窗口计算？昂贵且重复的计算适合物化
粒度是否稳定？一行到底代表事件、用户日、帖子日还是板块日？粒度不稳定时不要急着建汇总表
是否需要历史回溯？原始事件能否重算？迟到数据能否修正？需要重算就必须保留事实和血缘
是否有时效要求？报表要求秒级、分钟级还是每天更新？固定 SLA 决定预计算层级
存储和维护成本是否合理？是否会复制大量数据、增加同步任务和口径维护？收益小于维护成本时不要建
一个实用的经验判断是：如果一项计算同时具备“反复使用、计算昂贵、粒度稳定、需要固定时效”中的至少两到三项， 就值得认真评估是否建立数仓表；这不是硬性规则，最终还要看数据量和维护成本。

四、阶段 0：为什么原始事实表通常值得保留

原始事实表的粒度是“一行一个事件”，它不是为了让看板查询最快，而是为了保留事实和重算能力。

字段业务含义为什么保留
event_id事件唯一标识去重、追查重复上报
occurred_at行为发生时间按自然日重算、处理迟到事件
user_id登录用户身份用户级去重和身份过滤
anonymous_id匿名身份登录前后身份关联
event_name行为类型改变活跃口径时可以重新计算
properties事件扩展属性支持后续维度下钻
原始事实表通常值得保留，因为它是指标血缘的起点。即使今天只计算 DAU，未来也可能需要重新定义活跃、分析板块或回溯异常。

五、阶段 1：为什么建立合格事件层或清洗层

如果每个报表都重复写管理员过滤、事件列表和时间边界，就容易产生同名不同口径。

event_iduser_idevent_name是否登录普通用户是否有效事件合格事件层结果
E1U1page_view是是保留
E2U1post_view是是保留
E3U2reply_create是是保留
E4U2reply_create是是保留
E5U3login是否排除
E6NULLpage_view否，匿名是排除
E7U4post_view否，staff是排除

是否值得把这一层物化成表，要看它是否被多个指标重复使用：

情况建议
只有一个 DAU 查询，数据量很小直接 SQL 或 CTE
DAU、WAU、MAU、留存、用户分层都使用相同过滤建立可复用的清洗层或统一视图
每天都要扫描很大的事件表考虑物化合格事件层或按日分区

六、阶段 2：为什么建立用户日表

合格事件继续按 activity_date + user_id 汇总，得到一行一个用户每天的行为特征。

activity_dateuser_idevent_countpage_view_countpost_view_countreply_countis_new_user
2026-08-10U12110FALSE
2026-08-10U22002TRUE
2026-08-10U30000TRUE

这里发生了两个重要变化：

变化事件层用户日层业务价值
行粒度一行一个事件一行一个用户每天可以做用户分层和行为画像
U1 的两条事件2 行1 行适合计算 DAU，而不是事件量
U3 新注册无行为没有有效事件仍可保留 1 行避免新增激活率分母丢失
用户日表值得建立的原因是：它被 DAU、用户分层、新增激活、发帖率、回复率和留存分析反复使用，且粒度“一个用户一天一行”稳定明确。

七、阶段 3：为什么建立产品日表

用户日表继续汇总到日期粒度，形成看板直接读取的一天一行结果。

metric_datedausession_countpage_viewspost_viewsreplies_createdgenerated_at
2026-08-10221122026-08-11 00:10
业务需求直接查询事件表读取产品日表
管理员打开 DAU 趋势图每次扫描和去重读取一天一行，速度稳定
临时改变活跃口径灵活不灵活，需要重新生成
核查某个用户为何活跃可以回查事件只有汇总数字，不能单独解释
产品日表值得建立，是因为看板反复读取固定指标；但它不能替代原始事件表和用户日表。 汇总表是加速层，不是事实唯一来源。

八、阶段 4：事实表和维度表如何判断

数据仓库不只有“原始表”和“汇总表”。还要判断哪些数据属于事实，哪些数据属于描述事实的维度。

表类型一行代表什么适合保存的内容当前论坛示例
事实表 Fact一次发生的业务行为时间、用户、对象、行为、金额或数量analytics_analyticsevent、帖子、回复
维度表 Dimension一个可被分析的实体属性用户、板块、帖子名称、分类、状态auth_user、forum_board、forum_post
桥接表 Bridge多对多关系中的一条关联用户与帖子、用户与角色、帖子与标签帖子点赞用户关系
快照表 Snapshot某个时间点的状态当前点赞数、用户状态、帖子状态每日帖子状态快照

用表的变化判断是否值得建立

业务问题事实记录需要的维度是否需要新表判断理由
今天有多少普通用户活跃？AnalyticsEvent用户身份属性建立用户日表每天重复计算，且多个指标复用
哪个板块 DAU 下降？AnalyticsEvent.board_idBoard 名称和分类建立板块日汇总固定看板需要快速读取
某个用户为什么被计入 DAU？AnalyticsEvent 明细auth_user不建新表一次性回查，原始表足够
帖子获得回复的速度如何？Post、Reply作者和板块建立帖子回应中间表需要按帖计算首次回复时间
临时验证一个新事件口径AnalyticsEvent不需要使用 CTE需求尚未稳定，不应提前物化
建表的依据不是“原始数据已经有了”，而是“这个业务转换是否稳定、重复、昂贵、需要被多个使用者共享”。

九、表类型选择：CTE、视图、中间表还是汇总表

对象何时使用保存时间当前论坛案例
直接 SQL一次性、简单查询不保存临时核查 DAU
CTE（WITH）当前 SQL 内需要多个步骤当前查询期间事件过滤 → 用户去重
视图 View逻辑需要复用，但实时性优先保存定义，不保存结果统一普通用户有效事件口径
中间表重复计算昂贵且粒度稳定长期保存UserActivityDaily
汇总表 Mart固定报表和看板反复读取长期保存ProductMetricsDaily
事实表保存不可丢失的业务行为长期保存AnalyticsEvent、forum_post、forum_reply

十、建立一张表前必须写出的表合同

合同字段以 UserActivityDaily 为例
表名analytics_useractivitydaily
一行代表什么一个普通用户在一个自然日的行为汇总
唯一键activity_date + user_id
来源表analytics_analyticsevent + auth_user
时间口径Asia/Shanghai 自然日
过滤规则排除匿名、staff、superuser；保留有效行为
刷新方式按日生成，可重跑指定日期
下游使用者DAU、用户分层、新增激活、留存分析
质量检查唯一键不重复、计数不为负、与事件层 DAU 对账
如果一张候选表无法写清楚“一行代表什么、从哪里来、多久刷新、谁使用、如何核验”，就说明它还没有达到建表条件。

十一、最终判断流程

问题 1：是否保留事实？

如果数据代表真实业务行为，未来可能重算或追溯，建立事实表。

问题 2：是否重复使用？

如果多个指标都重复同一过滤和连接，建立视图或清洗层。

问题 3：是否计算昂贵？

如果每天反复扫描大表、去重和聚合，建立中间表或汇总表。

问题 4：粒度是否稳定？

如果不能明确一行代表什么，先不要建表，先完善指标合同。

  • 原始事实表解决“事实能否追溯和重算”。
  • 清洗或中间表解决“同一业务规则是否重复实现”。
  • 用户日表解决“用户级行为是否需要反复分析”。
  • 产品日表解决“固定看板是否需要快速读取”。
  • 事实表解决“业务行为过程是否需要保留”。
  • 维度表解决“事实发生在什么用户、板块或帖子上”。
  • 汇总表只在具体分析问题稳定且重复出现时建立。
建表不是“数据越多越好”，而是把稳定、重复、昂贵、需要追溯的业务计算沉淀下来。 最好的顺序是：先定义业务问题，再确定粒度，最后决定是否物化成表。

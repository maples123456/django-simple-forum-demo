论坛数据仓库：结构设计、数据来源与更新

用论坛 DAU、内容互动和留存这些真实业务问题，完整走一遍数据仓库设计： 从数据源盘点，到分层建表，再到增量更新、重跑、迟到数据和看板服务。

一、先从业务问题开始，而不是先画表

数据仓库不是把所有数据复制几份，而是把稳定、重复、昂贵、需要复核的业务计算沉淀到合适的粒度。
业务问题需要的事实需要的维度最终结果粒度
今天有多少登录普通用户活跃？浏览、发帖、回复、点赞事件用户身份和管理员状态日期
用户每天做了什么？有效事件用户、新用户标记日期 × 用户
哪个板块活跃下降？带 board_id 的事件板块名称和状态日期 × 板块
新用户 D1/D7 是否回来？注册日期和后续有效事件用户身份注册 Cohort × 留存日
为什么某帖子没有回应？帖子创建和回复事件帖子、作者、板块帖子
如果还不能写清楚“业务问题、分子、分母、时间窗口、去重键和一行代表什么”，先不要急着建汇总表。

二、论坛项目的数据来源

当前项目有两类主要来源：业务数据库事实和分析事件事实。

来源系统实际表主要字段记录什么更新特征
Django 用户系统auth_userid、date_joined、is_staff、is_superuser用户身份和注册信息新增、属性修改
论坛业务库forum_boardid、name、created_at板块实体低频新增和修改
论坛业务库forum_postid、board_id、author_id、created_at、updated_at帖子事实和帖子实体新增、编辑
论坛业务库forum_replyid、post_id、author_id、created_at回复事实通常只新增
React / Django 埋点analytics_analyticseventevent_id、event_name、occurred_at、user_id、anonymous_id、session_id、board_id、post_id浏览、登录、发帖、回复、点赞等行为追加写入，可能迟到或重复
业务关系表forum_post_likespost_id、user_id当前点赞关系新增或删除关系
事件表记录“发生过什么行为”；业务表记录“当前或最终业务对象是什么”。例如取消点赞事件能从事件表看到过程， 但 forum_post_likes 通常只反映当前关系，不能替代行为事实。

WITH deduplicated_events AS (
    SELECT *
    FROM (
        SELECT
            e.*,
            ROW_NUMBER() OVER (
                PARTITION BY event_id
                ORDER BY received_at DESC
            ) AS row_number
        FROM analytics_analyticsevent AS e
    ) AS ranked
    WHERE row_number = 1
)
SELECT e.event_id, e.event_name, e.occurred_at, e.user_id
FROM deduplicated_events AS e
JOIN auth_user AS u ON u.id = e.user_id
WHERE u.is_staff = FALSE
  AND u.is_superuser = FALSE;

八、阶段 4：中间表如何从事实粒度转换

以 DAU 为例，先从事件事实转换到用户日粒度：

activity_dateuser_idevent_countpage_viewspost_viewsrepliesis_new_user是否进入 DAU
2026-08-10U12110FALSE是
2026-08-10U21001TRUE是
2026-08-10U30000TRUE否，保留为激活率分母
下面的 AT TIME ZONE、FILTER 和 ON CONFLICT 是 PostgreSQL 示例。 项目默认也支持 SQLite；在 SQLite 中应由 Django/Python 先完成时区转换和 upsert，或改写为 SQLite 对应语法。 
INSERT INTO analytics_useractivitydaily (
    activity_date, user_id, event_count,
    page_view_count, post_view_count, reply_count
)
SELECT
    CAST(occurred_at AT TIME ZONE 'Asia/Shanghai' AS DATE),
    user_id,
    COUNT(*),
    COUNT(*) FILTER (WHERE event_name = 'page_view'),
    COUNT(*) FILTER (WHERE event_name = 'post_view'),
    COUNT(*) FILTER (WHERE event_name = 'reply_create')
FROM stg_effective_events
GROUP BY 1, 2
ON CONFLICT (activity_date, user_id)
DO UPDATE SET
    event_count = EXCLUDED.event_count,
    page_view_count = EXCLUDED.page_view_count,
    post_view_count = EXCLUDED.post_view_count,
    reply_count = EXCLUDED.reply_count;

十、数据更新：先区分三种时间

时间字段含义用于什么
occurred_at用户行为实际发生时间指标日期归属
received_at系统收到事件的时间增量抽取和延迟监控
generated_at指标表生成时间判断数据是否刷新
不能只用 received_at 作为业务日期。事件可能 09:10 发生、09:16 才收到；指标应该按 occurred_at 归属，但抽取任务可以按 received_at 找新增数据。

十一、数据更新策略

数据对象推荐更新方式依据字段是否允许重跑
AnalyticsEvent追加写入 + event_id 去重received_at、event_id允许补历史
用户维度增量 upsert 或每日快照id、date_joined、属性更新时间允许重建指定日期
帖子/回复事实按 created_at 增量，按 updated_at 修订帖子created_at、updated_at允许日期范围重跑
UserActivityDaily按日期删除后重建，或唯一键 upsertactivity_date必须允许
ProductMetricsDaily依赖中间层重算后 upsertmetric_date必须允许

11.1 事件增量抽取

SELECT *
FROM analytics_analyticsevent
WHERE received_at > :last_received_at
  AND received_at <= :current_received_at
ORDER BY received_at, event_id;

不要只使用“上次最大时间”而不保留边界和唯一键。相同时间戳的多条事件需要用复合游标：

WHERE (received_at, event_id) > (:last_received_at, :last_event_id)
ORDER BY received_at, event_id;

十二、迟到数据、未完结日期和重跑

问题具体表现处理方式
迟到事件08-10 发生，08-11 才收到按 occurred_at 回写 08-10，重算受影响日期
重复事件同一 event_id 被上报两次唯一键或 ROW_NUMBER 去重
当前自然日未结束今天上午只收到部分行为标记 partial，不作为正式历史结果

任务失败用户日已更新，产品日未更新按 run_id 和依赖顺序重跑

清洗事件原始批次完成合格事件否，用户日会不完整
生成用户日清洗层完成用户 × 日期否，产品日会错误
生成产品日用户日完成日期指标看板应显示上次成功时间

十四、如何判断一张候选表值得建立

判断项问题满足时的倾向
重复使用是否被多个指标、报表或团队使用？值得统一建表
计算成本是否需要大表扫描、复杂连接或跨日去重？值得预计算
粒度稳定是否能明确唯一键和一行代表什么？具备建表基础
时效要求是否要求固定刷新时间或查询 SLA？值得物化
可追溯是否能说明来源、过滤和重算方式？可进入正式数仓
维护成本是否增加大量同步、存储和口径维护？成本过高时不要建
最终决策可以概括为：业务价值 × 使用频率 × 计算成本 × 稳定粒度，再与存储和维护成本比较。 原始事实表负责可追溯，中间表负责复用，汇总表负责服务固定消费。

十五、从今天开始的实际实施顺序

顺序具体动作交付物完成标准
1盘点用户、帖子、回复、板块和事件来源数据源清单知道每个字段来自哪里
2确定 DAU、内容互动和留存指标合同指标定义文档分子、分母、时间和去重明确
3保留原始事实并建立唯一键ODS/原始层可以按来源主键重算
4建立清洗规则和质量检查Staging 层身份、事件、时间统一
5建立用户日表和帖子日中间表Intermediate 层唯一键稳定，可重复重跑
6建立产品日和板块日汇总表Mart 层看板读取快速且可对账
7配置增量水位、失败重试和迟到回补更新任务和运行日志数据更新可观察、可恢复
8用事件层与汇总层定期对账数据质量报告发现口径或刷新不一致
数据仓库设计的终点不是“表建得最多”，而是：业务问题有稳定口径，数据来源可追溯，更新过程可恢复，报表结果可解释。

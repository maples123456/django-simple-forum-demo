论坛产品日表：含义与指标为什么这样设置

产品日表不是“把所有指标放在一张表里”，而是把论坛每天最重要、最稳定、最常被读取的结果， 固定到“日期 × 产品”的粒度。本文从用户日数据和事件明细出发，解释每组指标回答什么问题、为什么需要、分母是什么，以及不能误解成什么。

一、产品日表到底是什么

ProductMetricsDaily 的一行代表：某个自然日的论坛产品整体指标快照。 它不是一行一个用户，也不是一行一个事件；它服务的是日趋势、日报和管理员看板。

AnalyticsEvent一次事件U1 在 09:01 浏览帖子事实追溯、重新定义口径
UserActivityDaily一个用户在一天的行为汇总U1 当天看了 2 个内容用户分层、用户级分析
ProductMetricsDaily一天的产品指标汇总08-10 DAU=2日趋势、管理看板

表的主键是 metric_date，所以同一个日期原则上只有一行。重跑日期应该更新这一行，而不是再插入一行。

三、指标设置的总原则：覆盖四类业务问题

规模

dau / wau / mau

有多少独立用户在使用论坛？

消费

page_views / board_views / post_views

用户是否在看内容、看了多少内容？

生产

posts_created / replies_created

社区是否持续产生内容和讨论？

互动

likes_created / interaction_users

内容是否获得回应和认可？

新增

new_users / activated_new_users

新增用户是否真正开始使用？

留存

d1 / d7 / d30_retention_rate

用户之后是否回来？

指标不是越多越好。产品日表优先保存“每天固定查看、口径稳定、可以支持业务判断”的指标；更细的分组和诊断放到其他表。

四、规模指标：DAU、WAU、MAU 为什么同时存在

字段业务问题时间窗口去重键为什么需要不能怎么解释
dau今天有多少人活跃？当天自然日user_id观察每日使用规模不等于用户满意度或留存
wau最近 7 天覆盖多少人？当天及前 6 天窗口内 user_id降低单日波动不能把 7 天 DAU 相加
mau最近 30 天覆盖多少人？当天及前 29 天窗口内 user_id观察月度用户池不等于月留存
 
-- DAU：当天独立用户
COUNT(DISTINCT user_id)
WHERE activity_date = :metric_date

-- WAU：窗口内重新去重，不能 SUM 每天 DAU
COUNT(DISTINCT user_id)
WHERE activity_date BETWEEN :metric_date - INTERVAL '6 day'
                        AND :metric_date

-- MAU：窗口内重新去重
COUNT(DISTINCT user_id)
WHERE activity_date BETWEEN :metric_date - INTERVAL '29 day'
                        AND :metric_date;
日期当天活跃用户DAU7 日窗口用户WAUDAU/WAU
08-10U1、U22U1、U2、U3、U4450%

DAU/WAU 反映周活跃用户中当天也活跃的比例，粗略表示使用频率；它不是 D1 留存。

五、内容消费指标：为什么既要次数又要用户数

字段分子/数值含义回答的问题为什么不能只保留一个
page_viewspage_view 事件次数页面被打开了多少次？无法知道是很多人各看一次还是少数人反复刷新
page_view_users产生 page_view 的独立用户数有多少人进入论坛？无法反映单个用户浏览深度
post_views帖子浏览事件次数内容总消费量是多少？不能直接当作浏览用户数
post_view_users独立帖子浏览用户数多少用户看过帖子？不能反映重复阅读
session_count非空 session_id 去重数用户通过多少次会话访问？没有可靠 session_id 时会低估
用户page_view 次数post_view 次数session 数用户层解释
U1111进入并阅读一次
U2101进入但没有打开帖子
U3551同一会话反复阅读

汇总结果是 page_views=7、page_view_users=3、post_views=6、post_view_users=2。次数和用户数回答的是不同问题。

六、内容生产与互动指标：为什么同时记录动作数和用户数

字段动作量用户量可派生指标业务含义
发帖posts_createdposting_users发帖率、每发帖用户发帖数内容供给和创作者覆盖
回复replies_createdreplying_users回复率、每帖回复数讨论参与和回应深度
点赞likes_createdliking_users点赞率、人均点赞轻量反馈和内容认可
取消点赞unlikes_created当前表未保存取消点赞用户数点赞动作净变化识别撤回行为，但不是当前点赞状态
用户发帖数回复数点赞数用户类型示例
U1300高频创作者
U2020讨论用户
U3002轻互动用户
U4000只读用户
3 篇帖子 / 4 个 DAU 是“人均帖子数”，不是“发帖率”。发帖率的分子必须是发帖用户数，而不是帖子动作数。

七、新增、行为分层和留存为什么放在产品日表

字段组字段分子/分母业务问题设置理由
新增规模new_users当天注册普通用户数 / 无每天新增了多少用户？判断增长来源
新增激活activated_new_users注册日有效用户 / 新增用户新增是否开始使用？区分注册量和有效使用
行为分层read_only_users只浏览用户数活跃用户中有多少只读？观察阅读到互动的结构
行为分层interaction_users回复或点赞用户数有多少用户参与互动？衡量社区参与广度
行为分层creator_users发帖用户数有多少用户生产主题内容？衡量内容供给来源
留存d1/d7/d30_retention_rate目标日回来用户 / 注册 Cohort 用户用户之后是否回来？把规模和持续使用分开
当前项目的留存字段是注册 Cohort 留存，不是“当天 DAU 中多少人回来”。留存必须使用注册日期体系，不能把行为日期和 Cohort 日期混为一谈。

八、当前 ProductMetricsDaily 的字段从哪里来

产品日字段主要来源典型计算最终粒度
dau合格事件COUNT(DISTINCT user_id)日期
wau / mau窗口内合格事件窗口重新 COUNT(DISTINCT user_id)日期
page_views / posts_created / replies_created合格事件按 event_name 计数日期
page_view_users / posting_users / replying_users合格事件按 event_name 的 user_id 去重日期
read_only_users / interaction_users / creator_users用户日行为特征按优先级分类计数日期
d1/d7/d30_retention_rate注册用户 + 目标日事件retained_users / cohort_size注册日期
anonymous_uv / anonymous_page_views匿名事件anonymous_id 去重或事件计数日期
 
ProductMetricsDaily.objects.update_or_create(
    metric_date=day,
    defaults={
        'dau': eligible_events.filter(
            event_name__in=EFFECTIVE_EVENTS
        ).values('user_id').distinct().count(),
        'page_views': events.filter(
            event_name='page_view'
        ).count(),
        'posting_users': events.filter(
            event_name='post_create'
        ).values('user_id').distinct().count(),
    },
)

代码中的 update_or_create(metric_date=day) 体现了产品日表的更新语义：同一天重跑时更新当天结果，而不是插入重复日期。

当前项目实现中，dau 使用 EFFECTIVE_EVENTS 计算； session_count 则来自当天普通登录用户的事件集合，二者的事件口径不完全相同。 因此不能直接把“会话数 / DAU”解释成严格的有效行为会话深度，除非先统一 session 的过滤口径。

九、为什么这些指标不能全部合并成一个指标

错误合并方式实际混淆的概念正确拆分
用 event_count 当 DAU事件量 ≠ 用户量DAU 用独立 user_id，事件量单独记录
用 page_views 当访问用户浏览次数 ≠ 浏览用户数同时保存 page_views 和 page_view_users
用 posts_created / DAU 当发帖率动作比例 ≠ 用户参与比例posting_users / DAU 是发帖率
用每日 DAU 相加当 WAU跨日用户重复计数窗口内重新去重
把点赞数当当前点赞动作过程 ≠ 当前状态点赞动作、取消动作和当前关系分开
把 DAU/WAU 当留存频率 ≠ Cohort 留存留存按注册 Cohort 和目标日计算

十、匿名指标为什么要单独保存

当前产品日表同时保存登录用户指标和匿名访问指标，因为两类身份回答的是不同业务问题。

字段去重或计数对象回答的问题不能等同于
anonymous_page_views匿名 page_view 事件次数匿名浏览行为发生了多少次？匿名 UV
anonymous_uv匿名 page_view 的 anonymous_id 去重有多少匿名身份浏览过？全站独立访客
anonymous_visitors排除已与登录用户关联的匿名身份后去重还有多少访客没有回连到登录用户？匿名 UV
anonymous_registrations能通过 anonymous_id 和时间顺序归因的普通注册匿名访问转注册效果如何？全部注册数
anonymous_id匿名 page_view后续注册是否归因匿名 UV匿名访客
A1是U1，ID 相同是+1不计
A2是无否+1+1
A3是U2，ID 不同否+1+1
匿名 UV 上升不一定代表真实独立访客同比上升；如果 anonymous_id 丢失或登录前后没有正确回连，归因指标会受到影响。

十一、产品日表能回答什么，不能回答什么

问题产品日表能否回答需要回到哪一层
08-10 DAU 是多少？能ProductMetricsDaily
DAU 比昨天上涨还是下降？能ProductMetricsDaily
DAU 下降来自哪个板块？不能直接回答BoardMetricsDaily + 事件/板块维度
哪个用户被重复事件计入？不能回答AnalyticsEvent
新增用户为什么没有激活？只能看到总量UserActivityDaily + 事件明细
某帖子为什么零回复？不能回答帖子日中间表 + Reply
产品日表是“总览层”，不是“万能查询层”。当业务问题从“发生了多少”变成“为什么发生”，就必须下钻到用户、板块、帖子或事件粒度。

十二、建立产品日表前的最终检查

检查项合格标准
粒度明确一行是一个自然日，主键是 metric_date
指标合同每个字段都有业务问题、分子、分母、去重和时间窗口
来源能够回溯到事件、用户日、注册 Cohort 或业务事实
一致性DAU 与事件层/用户日层可以对账
完整性未完结自然日有明确标记，不与完整日混比
更新同一天可重跑，不能产生重复日期或重复累加
边界知道哪些问题必须下钻到其他表
产品日表的设计目标可以概括为：用一行回答“论坛今天整体怎样”，用其他粒度的表回答“为什么会这样”。

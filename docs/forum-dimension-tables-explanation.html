论坛数据仓库：维度表的意义

用论坛事件、用户、板块和帖子走一遍维度表：它为什么存在，怎样与事实表连接， 如何把“发生了多少”解释成“谁、在哪个板块、哪类帖子上发生了多少”。

一、先用一句话理解维度表

事实表记录“发生了什么”；维度表记录“这个事实发生在谁、什么对象、什么分类上”。

事实表 Fact

可计数、可聚合的业务发生记录。

U1 在 09:01 浏览了 P1

维度表 Dimension

解释事实的实体属性和分类。

U1 是普通用户；P1 属于技术交流

没有维度表时连接维度表后
U1、B1、P1、post_view用户 U1 在“技术交流”板块浏览了“新手教程”帖子
只有 user_id 和 board_id可以按用户类型、板块名称、帖子主题分组
只能统计数量可以解释数量来自哪个对象和哪个群体

二、阶段 0：原始事实和实体来源

当前论坛项目中，维度通常来自业务实体表，事实通常来自事件表或业务行为表。

来源表一行代表什么关键字段在数仓中的角色

forum_post一个帖子id、board_id、author_id、title、created_at帖子维度和帖子事实来源

三、阶段 1：没有维度属性的事实表能回答什么

先看标准化后的事件事实。它能准确计数，但还不能解释对象名称和用户属性。

fact_event_idevent_dateuser_keyboard_keypost_keyevent_name能直接回答
E1012026-08-10U1B1P1post_view帖子浏览次数
E1022026-08-10U2B1P1reply_create回复次数
E1032026-08-10U3B2P2post_like点赞次数
问题仅凭事实键能否回答缺少什么
技术交流板块有多少浏览？不能完整回答B1 对应的板块名称
普通用户和 staff 的行为量如何？不能安全回答用户身份属性
哪个帖子浏览高但回复少？只能按 P1/P2 下钻帖子标题和板块属性
总共有多少帖子浏览事件？可以回答只需要事实事件计数

四、阶段 2：连接用户维度，增加“谁”的解释

把用户属性单独放在 dim_user，事实表只保存 user_key，通过 key 连接。

user_keyuser_iduser_typeregister_dateis_staffis_superuser
U1U1普通用户2026-08-01FALSEFALSE
U2U2普通用户2026-08-10FALSEFALSE
U3U3staff2026-07-01TRUEFALSE
fact_event_iduser_keyevent_name连接后的 user_type是否进入普通用户指标业务解释
E101U1post_view普通用户是普通用户浏览内容
E102U2reply_create普通用户是新用户参与讨论
E103U3post_likestaff否内部账号不进入正式 DAU
 
SELECT
    f.event_date,
    u.user_type,
    COUNT(*) AS event_count,
    COUNT(DISTINCT f.user_key) AS active_users
FROM fact_event AS f
JOIN dim_user AS u
  ON u.user_key = f.user_key
WHERE f.event_name IN ('page_view', 'post_view', 'reply_create', 'post_like')
  AND u.is_staff = FALSE
  AND u.is_superuser = FALSE
GROUP BY f.event_date, u.user_type;
用户维度的意义不是增加 DAU 数字，而是让 DAU 可以按用户类型、新老用户、注册日期等属性解释和拆分。

七、维度表和事实表的连接粒度

连接方式事实粒度维度粒度风险
fact_event.user_key = dim_user.user_key一条事件一个用户正常的一对多分析连接
fact_event.board_key = dim_board.board_key一条事件一个板块正常的一对多分析连接
事件直接连接多条标签一条事件一个帖子多个标签可能产生连接扇出，事件数被放大
事实表连接未去重用户维度一条事件重复用户记录COUNT(DISTINCT) 和属性版本冲突
维度表不是“随便 JOIN 的描述表”。连接前必须确认维度键唯一；如果维度表同一个业务实体有多行历史版本，必须明确使用当前版本还是事件发生时的版本。

八、当前属性和历史属性：为什么会有维度版本

例如 U1 原来属于普通用户，后来被标记为 staff。分析历史事件时，可能有两种需求：

分析口径维度连接方式08-10 的历史事件如何归类
当前身份口径连接当前 dim_user全部按 U1 当前身份解释
事件发生时身份连接带 effective_from/effective_to 的历史维度按 08-10 当天有效版本解释
user_keyuser_iduser_typeeffective_fromeffective_to当前版本
U1-v1U1普通用户2026-08-012026-08-12否
U1-v2U1staff2026-08-13NULL是
当前论坛项目的 auth_user 是业务用户表，不等于已经实现了完整的历史维度。是否需要历史版本，要看业务是否要求“按行为发生时的属性”回溯。

九、什么时候值得建立维度表

判断问题值得建立维度表的信号当前论坛例子
是否被多个事实复用？用户同时出现在事件、帖子、回复和点赞中值得建立 dim_user
是否需要频繁下钻？经常按板块、作者、帖子分类比较值得建立 dim_board、dim_post
属性是否复杂？包含分类、状态、来源、层级或历史版本维度表更容易统一管理
属性是否稳定且很少使用？只有一次分析且字段很少可以直接 JOIN 业务表
是否只是一个指标结果？例如当天 DAU 数字应放产品日表，不是维度表

十、维度表不能替代什么

误解实际问题正确做法
维度表里有用户，所以可以计算 DAU维度只知道用户存在，不知道当天是否行为事实表按日期统计行为，再连接用户维度
维度表里有帖子，所以可以知道帖子被看了多少次帖子维度没有浏览事件连接帖子维度和浏览事实
把板块名称直接复制到产品日表产品日表粒度是日期，混入板块会破坏粒度建立 BoardMetricsDaily 或板块维度下钻
维度表更新后历史指标自动正确当前属性可能覆盖历史状态明确当前口径或历史版本口径

十一、最终理解

事实发生了多少事件
+
用户维度谁发生了行为
+
板块/帖子维度在哪里、什么内容
→
可解释指标按维度下钻和诊断
  • 事实表负责计数和聚合。
  • 维度表负责解释、筛选、分组和下钻。
  • 维度表的核心不是增加数据量，而是统一实体属性。
  • 用户、板块、帖子适合做维度，因为它们被多个业务事实反复引用。
  • 连接维度前必须确认维度键唯一，并明确当前属性还是历史属性。
  • 产品日表保存总体指标，维度表支持解释总体指标来自哪里。
最终可以这样记：事实表告诉你“发生了什么”，维度表告诉你“这件事属于谁、哪里、什么对象”，产品日表告诉你“今天整体怎样”。

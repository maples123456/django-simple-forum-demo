论坛 DAU：什么时候使用 WITH

用当前论坛项目的真实表结构，解释 CTE（公共表表达式）如何把事件明细转换成 DAU， 以及什么时候应该使用它、什么时候直接写 SQL、什么时候需要真正的中间表。

先记住一句话

WITH 不是必须的“临时表”，而是把复杂查询拆成有名字的中间步骤。 它最有价值的地方是让过滤、连接、去重和汇总可以分别检查。
AnalyticsEvent一行一个事件
→
eligible_events普通用户的有效事件
→
eligible_users一行一个活跃用户
→
DAU一个统计数字

事件层

6目标日期的事件行数

用户层

1有效活跃用户行数

指标层

1最终 DAU 数值

二、WITH 在这条 SQL 中做了什么

WITH eligible_events AS (
    SELECT
        e.id AS event_id,
        e.user_id,
        e.event_name
    FROM analytics_analyticsevent AS e
    JOIN auth_user AS u
      ON u.id = e.user_id
    WHERE e.occurred_at >= :day_start_utc
      AND e.occurred_at <  :next_day_start_utc
      AND u.is_staff = FALSE
      AND u.is_superuser = FALSE
      AND e.event_name IN (
          'page_view', 'board_view', 'post_view',
          'post_create', 'reply_create', 'post_like'
      )
),
eligible_users AS (
    SELECT DISTINCT user_id
    FROM eligible_events
)
SELECT COUNT(*) AS dau
FROM eligible_users;
1
eligible_events：定义合格事件
连接用户表，排除匿名用户、staff、superuser，并保留有效事件。
2
eligible_users：从事件粒度转换到用户粒度
同一用户当天有多条有效事件时，使用 DISTINCT user_id 只保留一行。
3
最终查询：统计用户行数
此时每行已经代表一个活跃用户，因此 COUNT(*) 就是 DAU。
SQL 层级表或集合的含义粒度主要操作
原始表analytics_analyticsevent事件时间、身份、行为过滤
第一个 CTEeligible_events合格事件保留业务需要的事件
第二个 CTEeligible_users用户DISTINCT user_id
最终结果dau指标COUNT(*)

JOIN 负责找到用户属性；u.is_staff = FALSE 负责排除工作人员； event_name IN (...) 负责定义活跃行为；DISTINCT user_id 负责去重。 它们解决的是四个不同问题。

四、不使用 WITH 也可以吗

可以。如果只需要一个最终数字，直接写一条查询更简洁：

SELECT COUNT(DISTINCT e.user_id) AS dau
FROM analytics_analyticsevent AS e
JOIN auth_user AS u
  ON u.id = e.user_id
WHERE e.occurred_at >= :day_start_utc
  AND e.occurred_at <  :next_day_start_utc
  AND u.is_staff = FALSE
  AND u.is_superuser = FALSE
  AND e.event_name IN (
      'page_view', 'board_view', 'post_view',
      'post_create', 'reply_create', 'post_like'
  );
写法最终结果适合场景中间结果是否容易检查
直接 COUNT(DISTINCT)DAU简单、一次性查询较困难
WITH eligible_eventsDAU需要解释事件过滤可以
WITH eligible_usersDAU需要明确用户粒度转换最清晰
如果你的任务只是“今天 DAU 是多少”，直接 SQL 足够。 如果你的任务是“解释 DAU 如何计算、核验为什么是这个结果”，使用 WITH 更合适。

五、什么时候应该使用 WITH

情况建议当前案例中的表现
需要多个处理阶段使用 WITH事件过滤 → 用户去重 → DAU
需要改变分析粒度使用 WITH事件粒度转换为用户粒度
需要排查中间结果使用 WITH可以单独查询合格事件和合格用户
多个指标复用同一筛选逻辑使用 WITHDAU、有效事件数、人均事件数共用合格事件
只有一个简单计数可以不用直接 COUNT(DISTINCT user_id)
结果要跨多个任务长期复用不要只用 WITH使用用户日表或产品日表

同一份合格事件计算多个指标

WITH eligible_events AS (
    SELECT e.user_id, e.event_name
    FROM analytics_analyticsevent AS e
    JOIN auth_user AS u ON u.id = e.user_id
    WHERE e.occurred_at >= :day_start_utc
      AND e.occurred_at <  :next_day_start_utc
      AND u.is_staff = FALSE
      AND u.is_superuser = FALSE
      AND e.event_name IN (
          'page_view', 'board_view', 'post_view',
          'post_create', 'reply_create', 'post_like'
      )
),
eligible_users AS (
    SELECT DISTINCT user_id
    FROM eligible_events
)
SELECT
    (SELECT COUNT(*) FROM eligible_users) AS dau,
    (SELECT COUNT(*) FROM eligible_events) AS effective_events,
    ROUND(
        1.0 * (SELECT COUNT(*) FROM eligible_events)
        / NULLIF((SELECT COUNT(*) FROM eligible_users), 0),
        2
    ) AS events_per_dau;

六、WITH、真实临时表和数仓表的区别

对象存在时间能否跨查询使用当前项目用途
CTE：WITH当前 SQL 执行期间不能拆解和核验一次查询
真实临时表会话期间或手动删除前可以，在同一会话内复杂多步分析、需要索引
用户日表长期保存可以保存用户每天的行为汇总
产品日表长期保存可以保存每天的 DAU 等固定指标
不要因为查询很长就自动创建真实临时表。判断标准是： 只在当前查询中拆步骤，用 WITH；需要跨查询、建立索引或长期复用，才考虑真实临时表、中间表或物化视图。

七、最终判断流程

查询是否只有一步？简单过滤和计数
→
是直接 SQL
→
否拆成多个阶段
→
WITH命名并检查中间结果
  • 只查一个数字：优先考虑直接 SQL。
  • 有过滤、连接、去重、分组等多个阶段：考虑使用 WITH。
  • 需要看到每一步结果：使用 WITH，并暂时查询 CTE 本身。
  • 需要长期保存或供多个查询复用：使用用户日表、产品日表或真正的中间表。
  • 不要把“用了 WITH”误认为“性能一定更好”；它首先是结构和可核验性工具。
